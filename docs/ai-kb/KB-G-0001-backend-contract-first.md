# KB-G-0001 バックエンド契約を先に確認する

手順の正本はこの guide 自身である。

## 背景

KB-R-0003 の要約：あるプロジェクト（2026-11-07〜08）で、モバイル側のフィルタが効いていないように見えたが、真因はバックエンドの GET /tasks が status / themeId パラメータを読んでいなかったことだった。クライアント側のフィルタは無言で無効化されていた。バックエンド修正で解消した。

## 推奨手順

1. **エンドポイントの存在確認**
   - クライアントが呼ぶ正確なパスとメソッドについて、バックエンドのルート表・ハンドラを先に読む。
   - パスに対応するルートがなければ契約欠如とし、バックエンドが提供するまでクライアント作業を止める。
   - 確認したら、ルートファイルとハンドラ名を報告に残す。
2. **パラメータが効いているかの確認**
   - ハンドラ本体を読み、クライアントが送る各パラメータに対して何をしているかを列挙する。
   - 結果が異なるはずの検証データと、パラメータ値ごとの期待値を用意する。
   - 実エンドポイントを異なるパラメータ値で2回呼び、それぞれの応答を期待値と比較する。
   - 不一致の場合は「契約不整合の疑い」とし、ハンドラのコードやログで原因を確認する。
   - 2回の呼び出し（パラメータ値）、期待値、比較したフィールドを記録する。
3. **バックエンドを先に直す**
   - 契約確認が失敗したら、バックエンド修正をクライアント修正より先に着地させる。
   - 修正後、手順1（エンドポイント存在確認）と手順2（2回呼び出し確認）を再実行してから、クライアント変更を受け入れる。
   - 報告では、契約の確認結果をクライアントの結果より前に、エンドポイントとパラメータ名を明示して示す。
   - 不足するバックエンド挙動をクライアント側で覆い隠す修正は入れない。バックエンドがブロッカーであると明言する。

## 例外

- **エンドポイント自体を新規に作る作業**：契約は実装と同時に定義するため、この手順の代わりに契約を文書化する。
- **到達可能な実環境がない場合**：ハンドラのコード確認のみとし、実環境での2回呼び出し確認は未実施であることを報告に明記する。

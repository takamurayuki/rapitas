# ラピによる自動実行の監督

自動実行の監督を、外部のオペレーター（現在は Claude Code のセッション）からラピへ段階的に移すための設計メモです。権限は行動の種類ごとに渡し、渡す前に過去の判断との一致率で精度を測ります。

## 背景

2026-11-23〜24 の自動実行は、外部のオペレーターが常に監督して回っていました。2日間で rapitas 自体の修正 PR が約28件（#1688〜#1715）あり、質問への代理回答、停止の解除、反映（デプロイ）、CI の再実行を人の代わりに行っています。直近14日間の実績は次のとおりです。

| 指標 | 値 |
| --- | --- |
| 着手したタスク | 28件 |
| 完了したタスク | 20件 |
| 一度でもブロックされたタスク | 19件 |
| 回答待ちになった質問 | 22件（うち16件はオペレーターの代理回答） |

監督がいなければ、このうち多くはその場で止まります。監督の役割を製品の中に持たせることが、放置して任せられる自動実行への前提です。

## 現在あるもの

- `rapitas-backend/services/assistant/supervision.ts` は、人を待っているタスクを分類して件数で返します。読み取り専用で、モデルを使いません。分類は `held`・`noTheme`・`blocked`・`stalled`・`overdue` の5つです。
- 監視の部品は個別にあります。ブロックの通知、キュー停滞の検知、選定なしの検知（`auto-run-no-selection-watch.ts`）、CI の監視などです。
- オペレーターの判断は記録に残っています。代理回答は `question_resolved`（`sourceLabel: オペレーター代理回答`）、停止の解除は `halt_released`（理由 `hypothesis` 付き）として `WorkflowTransition` にあります。

足りないのは、止まっている理由をまとめて説明することと、判断して実行することです。

## 監督作業の分類

オペレーターが行っていた作業を、ラピへの移しやすさで分けます。

| 作業 | 例 | 移しやすさ | 理由 |
| --- | --- | --- | --- |
| 状況の報告 | 進捗のまとめ、止まっている理由 | 高 | 件数と記録を読めば書ける |
| 定型の操作 | CI の環境要因による再実行、空き時間の反映 | 高 | 実行の条件が機械的に決まる |
| 停止の解除 | 原因が解消した停止を解く | 中 | 原因の解消を確かめる必要がある |
| 質問への回答 | 推奨案の選択 | 中 | 推奨案はあるが、仕様の判断が混ざる |
| 原因の診断 | 重なり待ちの循環、依存のバージョン違い | 中 | ログと DB を突き合わせる |
| rapitas 自体の修正 | #1702〜#1715 | 低 | ラピは直接書かず、rapitas のテーマへ起票する |

## 段階的な権限移譲

権限は行動の種類ごとに、次の4段階で渡します。ある種類が次の段階へ進むかどうかは、その種類の一致率で決めます。

```mermaid
flowchart LR
  S1["段階1 説明する<br/>止まっている理由をまとめる"] --> S2["段階2 提案する<br/>行動案を作り人が承認する"]
  S2 --> S3["段階3 任せる<br/>一致率の高い種類だけ自動で実行する"]
  S3 --> S4["段階4 直す<br/>rapitas の不具合を証拠つきで起票する"]
```

| 段階 | ラピがすること | 人がすること | 次へ進む条件 |
| --- | --- | --- | --- |
| 1 説明する | 止まっている理由を分類して報告する | 読んで判断する | 理由の分類が実際の原因と合っている |
| 2 提案する | 項目ごとに行動案と根拠を作る | ワンクリックで承認か却下 | その種類で一致率が基準以上 |
| 3 任せる | 一致率の高い種類を自動で実行し、結果を報告する | 報告を読む。誤りは取り消す | 誤りの率が基準以下を保つ |
| 4 直す | 繰り返す不具合を証拠つきで rapitas のテーマへ起票する | 起票の優先度を決める | — |

一致率の基準は、同じ種類で20件中19件以上を初期値とします。件数が少ないうちは段階を上げません。

## 人に残す判断

次の判断は、段階にかかわらずラピに渡しません。

- 保護されたパスの変更（`services/agents/verification/`、`.github/workflows/` など。`.claude/CLAUDE.md` の一覧）
- 仕様の判断。質問の選択肢に `mutatesGate` または `requiresOperatorAction` が付いているもの、受入基準や要件文書を変えるもの
- 予算の上限を超えて続行すること
- 取り消せない操作。タスクの削除、強制プッシュ、他者の PR のマージなど

## 正解データによる事前照合

段階2の提案を本番に出す前に、過去のオペレーターの判断と照らし合わせます。

1. `question_resolved` の記録から、質問ごとに `question.md` の `json:options` の推奨案（`recommended`）と、実際に選ばれた選択肢（`selections`）を取り出す。
2. 質問の種類（`kind`）と、`mutatesGate` などの印の有無ごとに、推奨案と選択の一致率を集計する。
3. 一致率が基準を超える種類だけを、段階2の対象にする。

最初の照合は「推奨案をそのまま選ぶ」方針を対象にします。ラピがモデルで判断する方針は、この方針より一致率が高い場合だけ採用します。

## モデルの構成

監督の仕事を3つの層に分け、モデルを使うのは判断の層だけにします。

| 層 | 仕事 | 使うもの | 理由 |
| --- | --- | --- | --- |
| 1 事実を集める | 件数、待ちの理由、CI の結果 | モデルを使わない（`supervision.ts` と同じ） | 数や状態は DB で確定できる |
| 2 判断する | 質問への回答、原因の診断、停止の解除 | Claude Fable 5.2（`claude-fable-5-2`、effort `high`） | 誤ると差し戻しと費用が増える |
| 3 伝える | 進捗のまとめ、通知の文章 | Claude Sonnet 5.5（`claude-sonnet-5-5`） | 層1・2の結果を文章にするだけ |

- 呼び出しは既存の補助 AI の経路（`RAPITAS_AUX_AI=cli`、`claude --print`）に乗せ、モデルだけを指定します。
- 判断の層のモデルは、事前照合で Fable 5.2 と Opus 5.5（`claude-opus-5-5`）の一致率を比べて決めます。差がなければ費用が半分の Opus 5.5 にします。
- 監督は、作業するエージェント（実装は主に Codex、検証は Opus 5.5）と別のモデルにします。同じモデルが自分の出力を認める形を避けるためです。
- Fable 5.2 は1回の応答に数分かかることがあり、安全上の理由で断ることもあります。監督の呼び出しは非同期にし、断られたときは Opus 5.5 に引き継ぎます。

## 最初に起票するタスク

段階1と事前照合の2件を起票します。段階2以降は、この2件の結果を測ってから起票します。

| タスク | 内容 | 完了の確認 |
| --- | --- | --- |
| 監督の分類に回答待ちと停止を加える | `supervision.ts` に `awaitingAnswer`（回答待ちの質問）と `halted`（`haltReason` が残っている）を追加し、ラピの返答で件数と例を示す | 分類ごとのテストで、該当するタスクだけが数えられる |
| オペレーター判断の照合スクリプト | 上の手順で、推奨案と実際の選択の一致率を種類別に出す | 既存の記録で実行し、種類別の件数と一致率を出力する。テストは固定データで集計を確かめる |

## 測る指標

| 指標 | 定義 | 現在 |
| --- | --- | --- |
| 人の介入なしの完了率 | 完了したタスクのうち、オペレーターの代理操作の記録がないものの割合 | 未計測 |
| 提案の一致率 | 段階2の提案のうち、人がそのまま承認した割合 | 未計測 |
| 自動実行の誤り率 | 段階3の操作のうち、人が取り消した割合 | 未計測 |
